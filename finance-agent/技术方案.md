# finance-agent 技术方案

> 版本：0.1.0（演示/原型）  
> 定位：企业财务报销智能审批 Agent —— 从「上传票据 → 结构化 → 风控审批 → ERP 落单」的可观测流水线  
> 运维细节见仓库根目录 [运维指南.md](../运维指南.md)

---

## 1. 背景与目标

### 1.1 业务痛点

| 痛点 | 传统方式 | 本方案目标 |
| --- | --- | --- |
| 票据录入慢、易错 | 人工抄发票号/金额 | OCR + 规则抽取，自动回填表单 |
| 重复报销难发现 | 事后稽核 | 文件 SHA256 / 发票号 / 费用指纹实时拦截 |
| 制度难落地 | PDF 制度无人查 | 制度入库 + 向量检索（RAG）辅助校验与问答 |
| 审批路径不透明 | 经验派单 | 金额 + 风险规则生成审批链，步骤可观测 |
| 与 ERP 割裂 | 二次录入 | 预留 ERP 适配层（默认 mock） |

### 1.2 建设目标

1. **端到端演示闭环**：员工提交 → 自动风控 → 自动通过或待审 → 管理员处理 →（可选）ERP 凭证号。  
2. **人机协同**：低风险小额自动批；中高风险 / 超标进入人工。  
3. **证据留存**：票据原件落盘 + 单据台账入库，支持筛选、打款标记、批量导出。  
4. **架构对齐**：与同仓库 `rag-agent` / `cs-agent` 同构，便于对照学习与并行部署。

### 1.3 非目标（当前版本不做）

- 生产级发票验真（税务接口 / 版式模型）  
- 真实组织主数据、多级 OA 会签引擎  
- 真实 ERP 对接与会计科目映射  
- 多租户 / SSO / 细粒度 ACL

## 3. 技术选型

| 层次 | 技术 | 选型理由 |
| --- | --- | --- |
| 语言 / 运行时 | Python 3.12+ | 与同仓库 Agent 一致；AI 生态成熟 |
| Web | FastAPI + Uvicorn | 异步、OpenAPI 开箱即用 |
| 配置 | pydantic-settings + `.env` | 类型安全、环境隔离 |
| ORM | SQLAlchemy 2.0 asyncio + asyncpg | 异步单据读写 |
| 向量库 | Postgres + pgvector | 少组件；制度切片与业务库同实例 |
| 缓存 / 会话 | Redis | 登录 Token、多轮对话短期记忆 |
| 嵌入 | FastEmbed `BAAI/bge-small-zh-v1.5` | 本地可跑，免云端 Embedding 费用 |
| LLM | LangChain + OpenAI 兼容接口 | 制度问答；可换国内网关 |
| OCR | RapidOCR + Pillow + pypdfium2 | 中文票据；扫描 PDF 可栅格化再识别 |
| 导出 | openpyxl + UTF-8 BOM CSV | 规避 Excel 打开中文乱码 |
| 包管理 | uv + pyproject.toml | 锁定依赖；进程启动用 `python -m uvicorn` |
| 基础设施 | Docker Compose（pgvector/pg16 + redis:7） | 一键起库，无需本机装 PG/Redis |

## 4. 核心业务设计

### 4.1 智能审批流水线（8 步）

编排入口：`run_expense_pipeline`。每步产出 `PipelineStepResult`，前端可展示 OK/NG。

```text
上传原件(+可选手改 OCR 文本)
        │
        ▼
① receipt_parse     OCR/粘贴文本 → 金额、发票号、商户等（规则正则）
        │             票面金额优先于表单金额
        ▼
② duplicate_check   receipt_hash ∪ invoice_no ∪ fingerprint → 命中则 rejected
        │
        ▼
③ policy_retrieve   按类别+说明向量检索财务制度（RAG）
        │
        ▼
④ standard_check    餐费/差旅/交通等阈值校验（config 可配）
        │
        ▼
⑤ budget_check      部门预算预占（Redis/内存策略，驳回需释放）
        │
        ▼
⑥ risk_grade        综合重复/超标/置信度/金额 → low|medium|high
        │
        ▼
⑦ approval_route    生成审批链；decide_status →
                    auto_approved | pending_approval | rejected
        │
        ▼
⑧ erp_submit        仅自动通过时可 mock 提交，得到凭证号
        │
        ▼
落库 expense_records + 保存原件 data/receipts/<expense_id>/
```

**状态机（单据 `status`）：**

| 状态 | 含义 | 后续 |
| --- | --- | --- |
| `auto_approved` | 低风险且未超自动审批额 | 可 ERP；可标记已打款 |
| `pending_approval` | 需人工 | 管理员 `decide` → approved / rejected |
| `approved` | 人工通过 | 可选再推 ERP |
| `rejected` | 重复 / 高风险超标 / 人工驳回 | 预算释放（若曾预占） |

### 4.2 票据识别与防重

```text
文件字节 ──SHA256──► receipt_hash（全局唯一提交约束）
    │
    ├─ PDF 有文本层 → pdf_text
    ├─ PDF 无文本   → 渲染页 → RapidOCR → pdf_ocr
    └─ 图片         → RapidOCR → image_ocr
            │
            ▼
    receipt_parser（正则，兼容「发票号码」「票据号码」医疗财政票等）
            │
            ▼
    自动回填：金额、发票号、票据文本（前端选文件即触发 parse-receipt）
```

防重维度：

1. **相同文件内容**（`receipt_hash`）  
2. **相同发票号**（`invoice_no`）  
3. **费用指纹**（员工 + 金额 + 票号 + 说明摘要）

原件路径防穿越：按 `expense_id` 隔离目录，文件名清洗后落盘。

### 4.3 风险与审批策略（规则引擎）

**风险打分（示意）：** 重复 +50、超标 +25、OCR 置信度低 +15、大额分档 +10/+20 →  
`≥40 high` / `≥20 medium` / 否则 `low`。

**审批链：** 默认直属主管；金额或风险升高追加财务 BP、CFO。  
**自动通过条件：** 标准通过 ∧ 风险 low ∧ 金额 ≤ `auto_approve_limit`（默认 500）。

> 当前为可解释规则，非 ML 模型；调参需同步 `risk` 与 `approval.decide_status`。

### 4.4 制度 RAG 与问答

- 入库：文本分段 / PDF 抽取 → 切片 → 本地 Embedding → `rag_chunks`（pgvector）。  
- 审批链路：检索结果作为制度依据写入 steps / sources。  
- 问答：`run_policy_chat` **严格依据检索片段**回答，Redis 保存多轮，Postgres 落 `conversation_turns` 审计。

### 4.5 角色与权限

| 角色 | 演示账号 | 能力 |
| --- | --- | --- |
| user | zhangsan / lisi | 提交报销、看本人单据、制度问答、看本人原件 |
| admin | admin | 待审处理、全部单据筛选、打款、删除、批量导出、制度入库、代提 |

鉴权：登录发 Bearer Token，存 Redis（TTL）；接口依赖 `CurrentUser` / `AdminUser`。

### 4.6 管理闭环

- 筛选：状态 / 已打款 / 部门 / 工号 / 日期 / 关键词  
- 打款：`paid` + `paid_at` 手动标记  
- 删除：删库记录 + 原件目录  
- 导出 ZIP：`forms.xlsx` + UTF-8 BOM CSV + JSON + `receipts/`

## 5. 数据设计

### 5.1 Postgres 主要对象

**`expense_records`（报销台账）**

| 字段 | 说明 |
| --- | --- |
| expense_id | 业务单号 `EXP-…` |
| employee_* / department / category / amount / description | 申请主体与费用 |
| invoice_no / fingerprint / receipt_hash | 防重键 |
| receipt_path / receipt_filename | 原件定位 |
| status / risk_level / summary | 审批结果 |
| erp_voucher_id | ERP 凭证（mock 或真实） |
| approver_* / approval_note | 人工审批痕迹 |
| paid / paid_at | 打款标记 |
| created_at | 上报时间 |

**`conversation_turns`**：制度问答审计。  
**`rag_chunks` + embedding**：制度向量（启动时 `CREATE EXTENSION vector`）。

### 5.2 Redis

- 登录会话、对话短期历史  
- 不持久化报销主数据

        └── meta.json          # hash / path / size

## 8. 前端方案

- 技术：原生 HTML/CSS/JS（无构建），降低演示成本。  
- 登录后按 `role` 动态 Tab：用户侧「提交/我的/问答」；管理侧「待审/全部单据/制度」。  
- 选原件 → 自动 `parse-receipt` → 填充金额/发票号/OCR 文本。  
- 流水线结果展示每步状态；全部单据支持筛选与原件预览/下载（保留后缀）。

## 10. 质量与可观测性

- **步骤化结果**：每次提交返回 `steps[]`，便于对照失败环节。  
- **健康检查**：`/health` 探测 Postgres、Redis。  
- **审计**：对话落库；原件 `meta.json` + DB 路径。  
- **测试建议**：样例票 `fixtures/sample_invoice.*`；换发票号/换文件测防重；超标与小额分别覆盖自动批/待审。

## 12. 风险与约束

1. OCR 受拍照质量影响；医疗财政票等已做标签增强，极端版式仍需人工改文本。  
2. 预算预占为演示实现，并发下需改为 DB 事务或专用预算服务。  
3. `auto_approve_limit` 等阈值写在配置，生产应来自主数据。  
4. Windows 下避免 `uv run` 长期占用 exe；用 `python -m uvicorn`。  
5. 首次 FastEmbed / RapidOCR 可能下载模型，需可用的 HF 镜像（`HF_ENDPOINT`）。

## 14. 结论

finance-agent 采用 **「可观测流水线 + 规则风控 + RAG 制度 + OCR 票据 + 角色化管理台」** 的技术方案，在单机 Docker 基础设施上即可演示完整报销审批闭环。当前适合培训、方案预研与产品原型；进入生产前需补齐身份体系、发票验真、真实预算/ERP 与对象存储等能力。
